# Stack frames and register storage (Phase 1.5)

## 1. LR is not saved (default)
Returns are translated to SM83 `ret` (the SM83 call stack holds the return address), so
the ARM LR value is never needed after a call. `tools/prune/frame.py` tracks SP offsets
and the save slots written by `push` / read by `pop`; a slot is not written (and the
pop does not load it) when every value read back from it is *useless*: not read by any
instruction except copies into useless values, and not the value of a register that is
live at a return. With the default ABI the registers live at a return are r0 and the
callee-saved r4-r11; LR is never live. `mov lr, r9; push {r7, lr}` (GCC saving r9 in
the LR slot) is therefore still saved, because the value flows back into r9.

## 2. Entry ABI opt-in (`--entry-abi none`)
For the **program entry only** (the kernel called by the game/harness), the registers
live at its returns can be reduced to r0. The prologue/epilogue then skips saving and
restoring r4-r11. **ABI implication:** the caller must treat r1-r12 and LR as clobbered
by the call (like caller-saved registers). This is safe for the lockstep harness and for
code generated by this tool that calls kernels through a wrapper that saves what it
needs; it is NOT safe for arbitrary hand-written ARM callers that rely on AAPCS.
Callees keep the normal ABI.

Assumption shared by both: memory accesses through pointers to local objects stay
inside those objects (C semantics), so they never touch the register-save area.
